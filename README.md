- `src/EmbodySense.Core.Persistence` owns long-lived `.agent/` and workspace state access, including audit events, conversation transcripts, system and custom loop definitions, immutable contextual-role revisions and lifecycle evidence, guarded registered-role-source inspection, custom run traces and tombstones, full governed tool-response artifacts, idempotent invocation/control receipts, the custom-loop execution gate and exclusive single-host ownership lock, permissions loading, workspace context document reads, and scaffold file writes. - `src/EmbodySense.Core.Startup` owns concrete composition. ### Default-conversation durable turn protocol

Each admitted ordinary-chat turn has one strict schema-version-1 artifact under `.agent/loops/runs/default-conversation-turns/`. `Core.Application` owns its state machine; `Core.Persistence` only supplies atomic compare-and-advance storage. The artifact retains the exact base transcript, stable turn/run/user-message/user-publication/provider-attempt/provider-correlation/assistant-message/assistant-publication identities, desired run projection, provider response identity when observed, actionable review evidence, and a complete append-only transition history.

The checkpoints advance in this order: admitted; Started run projected; user accepted; user publication prepared; user published; provider dispatch prepared; the irreversible `turn/start` transport-write boundary durably marked; provider outcome observed; assistant publication prepared; assistant published; transcript synchronized; terminal status prepared; terminal run projected. Transcript appends use the retained conversation identity, version, exact prefix, message identity, and publication identity as one compare-and-append operation. Runtime state is replaced only from the resulting canonical durable snapshot, so it is no longer an independent commit that can silently outrun conversation memory.

Restart recovery holds the same workspace conversation lease used by live turns and classifies every nonterminal artifact. A pre-dispatch turn is closed without dispatch; an already committed user or assistant append is recognized by its exact identities rather than duplicated; an observed provider output is published and completed without another provider call; a conclusive provider-declared terminal failure is checkpointed and closed as `Failed` without quarantine or review; a missing terminal run projection is reconstructed from the checkpoint. If completion auditing fails after a successful response, the exact observed output is retained as `NeedsReview` without publication or redispatch; if auditing also fails after a conclusive provider failure, the attempt still closes as `Failed` with both failures retained. Once the durable marker immediately before the provider's `turn/start` transport write exists, any turn without a durably observed outcome becomes `NeedsReview` with its attempt and correlation identities and is never automatically repeated. The ambiguous transport is quarantined before later provider work, and `/review` plus `/review resolve <turn-id>` expose an explicit abandonment path without replay or publication. A replaced conversation identity, unexpected message, or divergent ordering is also `NeedsReview` unless a terminal provider failure was already durably observed; in that case recovery preserves the divergent user-owned transcript exactly while closing the known attempt as `Failed` and durably recording the conflict in its failure detail. A terminal review record continues to preserve the matching current conversation across later CLI starts until explicitly resolved or the user changes that conversation identity. Identityless pre-release transcript entries fail with an exact file path and explicit backup/removal guidance; they are never migrated or rewritten automatically. The injectable boundary failpoint, abrupt-process-loss test, and cross-process publication race cover every protocol write plus the raw transcript-append windows.

The older provider-neutral fenced-JSON tool protocol has been removed. Dynamic app-server tools are the only supported governed tool integration.

Default conversation/runtime governed commands:

- `list`: list a directory.
- `read`: read a file.
- `search`: search a file or directory for a text pattern.
- `write`: create or replace a file.
- `append`: append text to a file, creating it if needed.
- `delete`: delete a file or directory after delete permission or human approval.

Current app-server dynamic tool calls use `embodysense.command` with structured arguments:

```json
{"namespace":"embodysense","tool":"command","arguments":{"command":"read","path":"shared/notes.md"}}
```

Governed tool outcomes are retained before the 64,000-character model-facing formatter can truncate them unless retention explicitly reports unavailable. At a full quota, read/list/search inspection under the evidence root is returned without self-retention instead of evicting the evidence being inspected. A retained sensitive artifact lives under `.agent/logs/tool-responses/<request-id>/`: `manifest.json` records loop/run/request/audit correlation, outcome, exact SHA-256, character/UTF-8 sizes, and ordered chunk metadata, while UTF-16-safe 32,000-character chunks preserve the complete bounded response for later inspection. Responses are bounded at 160,000 characters; retention keeps at most 256 complete artifacts and 64 MiB, evicting only the oldest complete artifact under a cross-process workspace lock. Cached file stamps are used only for quota accounting; an artifact is fully rehashed before its reference is reused or it becomes an eviction victim. Eviction first atomically renames its victim to a recoverable staging name, and exact orphaned write or eviction staging directories are recovered under the lock. The returned model text places the manifest path and integrity metadata before output, so those references survive final truncation; a retention failure is explicitly reported instead of advertising partial evidence. Raw response content never enters audit. The general logs tree remains denied to agent tools, while the more-specific tool-response path requires human approval for read/list inspection.

Human-facing transcript controls are available from the CLI runtime host and the localhost Web UI. `/history`, `/conversations`, and `/load` load a saved transcript before the first model turn in the current session, replace the visible conversation transcript, and keep the restored messages in conversation runtime state. In the Web UI, `/history` lists stored conversations and the next submitted number loads that selection; successful loads emit a `history_loaded` stream event that replaces the browser transcript before the confirmation message is appended. `/cancel` cancels the pending selection. `/new` and `/new-session` start another fresh transcript without leaving the session. `/review` lists unresolved ordinary-chat evidence, and `/review resolve <turn-id>` explicitly abandons an inspected unknown outcome after provider quarantine without replaying the request or publishing an unproved response. Verbose mode can be changed from the Web UI toggle or with `/verbose`, `/verbose on`, and `/verbose off`; it prints the visible inference context EmbodySense is about to send for the next model turn and labels it as visible context, not private model reasoning or hidden chain-of-thought.

### Custom Loop MVP (Web)

The Web Loops surface supports multiple role-bound custom definitions whose persisted shape is Manual Trigger -> one to five ordered Inference steps -> Exit. Trigger, Exit, connectors, and layout are system projections rather than persisted arbitrary graph topology. The read-only system default is projected separately from its canonical five-node graph: Accept user message -> Assemble runtime context -> Dispatch provider inference -> Persist transcript -> Complete loop run. The UI exposes its actual human-message trigger, workspace startup-context scope, role, capabilities, review/failure policy, stable node and edge IDs, and system ownership without translating them into custom-loop authoring fields. Those nodes and edges are an `AuthorityTopologyOnly` projection: they describe governed ownership and boundaries but do not certify the dedicated runner's exact execution order. They are not dispatched by the custom-loop runtime or a generic graph executor, and ordinary chat still runs through the dedicated default runner.

Choosing Create starts a tab-scoped client draft and does not create a durable definition. That draft remains available in the same tab across Loops navigation, reload, and reconnect, but closing the tab or choosing Discard draft removes it; another tab receives an independent draft. An unsaved draft consumes no durable-definition quota, is absent from the published catalog and Runs view, and cannot be invoked. The first explicit Save sends the complete definition atomically under one stable operation ID. A retry after an uncertain response sends that exact request again, while catalog reconciliation recognizes an already committed operation without creating a duplicate. Known validation, authority, conflict, and quota failures remain visible without treating the local draft as saved.

Saved custom loops are server-validated, versioned, deleted, manually invoked from an exact saved version and content hash, paused at a proved checkpoint boundary, cancelled, explicitly resumed, and inspected through durable run evidence. Invoke switches to the Runs view while execution is active; the view refreshes any selected nonterminal run even after reload or reconnect. Deleted definitions remain available as archived run-history groups, and explicit trace-deletion tombstones remain selectable after reload without restoring deleted content. At most one nonterminal run exists per loop and one custom loop actively executes in the workspace; a busy request is rejected rather than hidden in a queue. A cancellation from another runtime or process is routed through the current workspace host's generation-scoped, capability-authenticated, current-user-only local IPC broker to the currently registered provider attempt or conversation-publication operation. Caller/deadline cancellation is tracked separately from the routed source so a provider interruption is confirmed only when no competing source won. The durable receipt distinguishes a confirmed provider cancellation exception from a delivered-but-unconfirmed signal, a run with no active cancellable operation, or an unavailable delivery route; owner exit or a routing timeout leaves the receipt pending for the same idempotent retry. Each pending Pause, Cancel, or Resume receipt also holds a cross-process execution lease and records its owner generation. A concurrent retry fails closed while that lease is live; after return or process exit releases it, the same explicit retry can claim a new generation and safely re-drive the orphaned pre-transition window. Startup recovery never dispatches work automatically: a safely interrupted run is parked as Paused, an uncertain open attempt becomes Needs Review, and a safely pending cancellation may be completed. If another process owns custom-loop hosting when the Web runtime starts, ordinary chat and its preserved transcript remain available; after that owner exits, the retained runtime may reacquire hosting, complete recovery under the same gate used by pause requests, and reconcile only an extension of the exact durable conversation identity before a later custom-loop retry can dispatch. Recovery integrity failure disables automatic reacquisition for that runtime. A replaced conversation identity, transcript divergence, or an unreadable transcript preserves local chat state, returns a structured failure, and releases hosting so another runtime can recover cleanly. Invocation receipts bind the stable logical-conversation identity and a content-only captured-context hash before admission, so reuse from a different conversation conflicts without persisting the prompt or context content in the receipt. A pre-dispatch terminal binding records its exact `NotFound`, `WorkspaceExecutionBusy`, or `Invalid` intent—including definition disappearance after context capture—and can only finish that no-dispatch outcome after interruption; it cannot upgrade into admission.

Before SignalR sends an invocation, the browser durably marks its prompt-free operation identity as dispatched; only a proved pre-dispatch transport failure rolls that mark back, so a tab restart cannot misclassify an uncertain send as a fresh request. If an invocation connection closes ambiguously, the browser queries the exact durable invocation receipt for up to ten seconds and distinguishes pending, admitted, rejected, unavailable, and still-unknown outcomes without replacing or clearing a run the user selected during that polling window, including when returned receipt identity is mismatched. A confirmed exact live run or retained tombstone releases the retry identity even if unrelated list, quota, or trace refreshes are temporarily unavailable. Unknown, receipt-unavailable, and previously dispatched host-unavailable outcomes are never reported as definitive start failures; a workspace-scoped, prompt-free browser registry and cross-tab lock preserve operation IDs for unchanged requests across tabs and tab restarts, and invocation fails closed if that shared reservation or dispatched state cannot be persisted. The browser identity includes the exact configured provider and model, matching the server receipt identity so a runtime configuration change starts a distinct operation without discarding the older pending evidence. Each tab releases only its own pre-dispatch reservation, and each unresolved request refuses a 101st concurrent browser reservation before persistence. When that registry reaches its bound, definitive rejection receipts—including audit-unavailable rejections with no run—are released directly, while receipts that name an admitted or audit-unavailable run require exact live-run or tombstone verification and unresolved identities are never evicted.

After reload or reconnect, a selected nonterminal run is monitored through a cached exact-ID index lookup and an opaque ETag bound to both the complete summary and canonical artifact hash. Standard weak, wildcard, and combined `If-None-Match` validators are honored. Unchanged polls return no body, including during long approval waits; verified compact metadata serves those polls without reopening the full trace or rescanning every loop directory, while filesystem change notifications invalidate the affected artifact binding and run-ID ownership caches. A watcher error discards affected certainty and recreates the watcher so complete canonical validation can re-establish lightweight caching. Every changed validator reloads workspace pages, quota, full run state, and trace evidence even when the compact summary is unchanged, because only `304 Not Modified` proves the artifact-bound evidence is current. A changed validator is retained only after that full refresh succeeds. If the monitor endpoint is unavailable, scheduled and in-flight monitoring fall back to ordinary full evidence with bounded exponential backoff; two exact-ID misses with no successful full-evidence read between them clear stale active evidence instead of abandoning a transient replacement or polling a permanent miss forever.

Run discovery uses immutable creation-order opaque cursors and a crash-repairable lightweight metadata index whose summaries are hash-bound to canonical artifacts, so continuation pages do not reparse every retained trace and independently modified derived summaries trigger repair. Canonical mutations remain successful if post-commit index maintenance is interrupted; a pending marker makes the next indexed read repair that derived state. The Web surface fetches the selected loop through the exact loop-id filter alongside workspace discovery, scopes pending continuation work to that loop, and progressively loads older live traces and tombstones without dropping the current selection. A committed deletion replaces the exact selected summary with its returned tombstone even when that run came from an older page. Deleted definitions remain available as archived history as older pages are discovered.

Completed custom-loop authoring, invocation, and lifecycle receipts remain replayable for at least 30 days. When a receipt write reaches its governed class ceiling, runtime admission may request one bounded cleanup; authenticated Web users can also inspect receipt-retention posture and explicitly request a bounded cleanup for one visible artifact class. No browser timer or background task starts cleanup. Cleanup never selects pending receipts or completed receipts newer than the replay cutoff. A cross-process mutation lease and one bounded durable batch journal bind the exact selected operation IDs, completion timestamps, hashes, and byte counts. The intent audit precedes deletion, and an outcome audit is attempted by one durable owner; an interrupted or failed audit attempt becomes a durable warning that later cleanup cannot overwrite. A selected receipt that changes or disappears without durable proof of deletion abandons the batch and is conflict-audited rather than attributed to the harness. Recognizable stale atomic-write temp files are removed under the mutation lock after restart, while malformed, oversized, unexpectedly named, over-count, or changed receipt artifacts otherwise fail closed before a new cleanup batch deletes anything. Audit-unavailable and corrupt-retention responses remain distinct from genuine quota exhaustion. After an expired receipt is pruned, that receipt alone no longer reserves its operation ID for replay, although surviving run evidence can still reconcile or reject a later request.

Lifecycle-control receipts use the same 30-day exact replay boundary with a separate 20,000-receipt, 128 MiB raw quota and finite compact idempotency-proof budget. At admission quota, the live runtime issues one bounded governed cleanup request and retries the same Pause, Cancel, or Resume receipt once only after cleanup commits; pending and newer receipts remain protected. A stale cleanup owner is recovered or safely terminalized after its 30-second ownership window instead of permanently blocking unrelated lifecycle controls. Cleanup removes only recognized inactive per-operation owner locks and abandoned atomic-write temporaries under the shared mutation lease, while active ownership, unexpected artifacts, and simultaneous raw-plus-compact evidence fail closed.

Trigger admission selects exactly one prompt source: the invocation prompt, a saved preset, or no prompt. It may also bind a bounded snapshot of the invoking logical conversation.
